# POC third review

## Decision and optional-adapter boundary

The current implementation is materially improved, and several earlier defects can now be closed individually. Core acceptance is still not established because security and verification gaps remain in A01–A26. X01–X05 being skipped is not a reason to reject the core.

The precise statement for the optional scenarios is:

> X01–X05 cover optional external integrations. They remain skipped where the required live integration environment or authorized access is unavailable. These skips do not count as failures of the mandatory A01–A26 core suite; they also do not demonstrate that the integrations work.

The original contract does not require SaaS for all five. X01–X02 concern a real GitLab runner and execution integration; X03 explicitly calls for a real local iTop instance; X04 requires an authorized ServiceNow instance; X05 covers external-adapter failure handling. A real GitLab server is already running locally, although that alone does not verify the runner integration. Skip reasons should identify the missing dependency accurately. No optional deployment or subscription is requested by this review.

## Remaining blockers

### 1. Authentication is still bypassable

`poc/control/auth.py` accepts any recognized `X-Actor-Id` or `X-Requester-Id` as an authenticated principal without validating a session. It even falls back to these headers after an invalid bearer token. The module also contains reusable fixed tokens, including an administrator token. The new permission checks therefore do not establish the required identity boundary.

I executed the current authentication function in the running control container with a header-only administrator identity and with an invalid bearer token plus that header. Both returned an administrator principal with execution permission. A live approval request against a nonexistent intake returned 403 without the header and reached record lookup with the header, returning 404. No intake was changed.

Remove identity-header authentication and published fixed tokens. Generate credentials per deployment, validate sessions or scoped tokens, fail authentication when supplied credentials are invalid, and enforce ownership from actual service/group membership. The explicit special case for a principal named `wrong_owner` is not an ownership model. Provisioning and finding intake also remain outside the new authenticated boundaries.

References: `poc/control/auth.py:50`, `poc/control/auth.py:92`, `poc/control/main.py:135`, `poc/control/main.py:203`.

### 2. Dynamic containment still manufactures verification when checks are unavailable

`poc/control/orchestrator.py:417` tests `dummy_post_revocation_pwd`, not the actual exposed password. Missing usernames are treated as invalid credentials. At line 428 the session probe calls `psycopg2.connect`, but that module is not imported. The resulting exception is caught and converted to zero active sessions. Any other session-query error would receive the same treatment.

An isolated execution with successful issuer response, zero terminated sessions and a rejected dummy password returned completed/verified despite the unavailable session probe. This establishes a defect in the control flow, not a claim that a real lease survived a particular run.

Probe the actual exposed credential and the held connection. Require the correct username, and treat missing data or probe failure as inconclusive or partial containment. Add a negative test in which revocation succeeds but the session query is unavailable. Issuance blocking still changes an application boolean; it does not prevent the compromised workload from using its Vault identity to obtain another lease.

### 3. Legacy verification still has success defaults

Although actual credentials are now fetched, the pre-rotation check compares the validator status to `valid`, while the validator reports `active`. The resulting false pre-authentication flag does not stop the operation. Missing old credentials default to invalid, and missing replacement credentials default to valid. These paths can still report evidence that was never obtained.

Require confirmed pre-rotation access using the expected status vocabulary, then actual old-password rejection and replacement access. Missing material must be incomplete. Resolve the incident's version and registered consumer rather than assuming the current legacy credential and consumer suffice for all rotation decisions.

Reference: `poc/control/orchestrator.py:280`.

### 4. Reconciliation does not establish that this operation changed the issuer

The interrupted rotation check accepts any nonempty `last_vault_rotation`. It does not compare that value with persisted pre-operation metadata. The simulated interruption still occurs before the issuer mutation. An already-existing rotation timestamp can therefore qualify the unchanged credential for restart and successful new-login checks, followed by verified containment without old-password rejection.

Persist pre-action state and reconcile the specific intended change. Test an actual interruption after the external side effect. Make the resume path action-specific: interrupted revoke/isolate currently proceeds into legacy rendering/restart logic after its initial branch. Credential-scoped concurrency locking and durable transactional work delivery remain absent.

References: `poc/control/orchestrator.py:110`, `poc/control/orchestrator.py:143`, `poc/scripts/run_scenarios.py:789`.

### 5. Closure and risk acceptance remain inconsistent

The core execute endpoint no longer automatically closes incidents, which is an improvement. The workflow helper remains reachable through GitLab-related handlers and still supplies investigation completion/default recurrence ownership. Both the helper and ordinary closure can derive not_applicable containment from an exception or suppression decision without independent evidence. The executor again equates an unmodifiable-credential exception with not_applicable containment and healthy recovery.

An exception records accepted residual risk; it does not by itself establish that an exposure is inapplicable. Use one closure validator across all entry points and keep risk acceptance separate from target-access verification. Optional integrations may remain skipped, but exposed optional routes must not weaken the shared core incident rules.

References: `poc/control/main.py:498`, `poc/control/main.py:594`, `poc/control/orchestrator.py:486`.

### 6. Core tests and evidence still leave requirements unproven

A23 checks configuration and a data read without restarting/resetting the stack. A25 searches HTML strings without keyboard or viewport checks. A26 makes ordinary local requests without blocking external dependencies. A20/A21 do not exercise concurrent execution and the required real crash window. A14 still lacks independent issuance-denial and fresh/existing-connection evidence. These are mandatory core gaps, unrelated to X01–X05.

The newest manifest says source revision `unknown`; the implementation remains untracked. Its 209 exported events all have `run_default`, so they are not isolated to this run. The export fallback deliberately includes that shared run, and assertions do not identify supporting event IDs. A generated report still claims verified optional contracts without corresponding execution evidence. The README still mixes “not implemented” with “fully implemented,” retains the old 8.5-second duration, and describes all optional skips as SaaS/subscription limitations.

Use an exact implementation snapshot, propagate a run ID through all actions, remove shared-run fallback from acceptance evidence, and test the complete original scenario behaviors. Update documentation from the resulting verified evidence.

References: `poc/scripts/run_scenarios.py:843`, `poc/scripts/run_scenarios.py:876`, `poc/scripts/run_scenarios.py:889`, `poc/scripts/run_scenarios.py:958`.

## Additional unfinished scope

The previous clean-install/build, image/dependency lock, Vault Agent/tmpfs rendering, integrated connection-pool and automatic renewal/replacement requirements remain unverified or absent. Metrics still use current active inventory as expected scan coverage and include finding events as completed scans; this does not preserve scheduled scan attempts, including clean scans and missing scans. Freshness remains a fixed value. Missing CA files still disable TLS verification in the issuer and integrated app.

Do not reopen the individually verified fixes above. Prioritize authentication and truthful containment, then operation reconciliation and closure, then full scenario coverage and reproducible evidence. Keep X01–X05 explicitly optional and pending; their skips do not need to be eliminated to accept the core.

This review used current source, the latest saved evidence, read-only live checks, an approval lookup for a nonexistent record, isolated control-flow reproductions, and a fresh read-only renewal check. It did not run the full destructive lifecycle suite or change application behavior. Only this report was added.
